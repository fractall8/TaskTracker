# Deferred Work

## Resolved by: post-manual-testing bug-fix + deferred-work sweep (2026-07-26)

Nearly everything below this section was fixed in this round — see the story's Change Log for the full
list. Two items were deliberately left as-is; the reasoning is captured where they originally appear
below rather than duplicated here. Only genuinely non-resolvable or consciously out-of-scope items
remain listed as still-open, each with its own reasoning inline.

## Deferred from: code review of 1-1-board-realtime-calls (2026-07-25)

- **Consciously not implemented (2026-07-26).** Global per-user single-active-call-across-boards constraint isn't enforced (a user could be "active" in calls on two different boards at once). This was speculative when first noted and remains so — no stated AC requires it, and the underlying multi-call scenario (a user starting/joining calls on two boards at once) isn't itself a broken or unsafe state, just an unusual one. Building a cross-board lock for a case nothing asks for would be scope creep beyond this story; revisit only if a real product requirement calls for it.
- **Resolved (2026-07-26).** No compensating cleanup for a partial ACS-Room-created/DB-insert-failed failure in the start flow. Both halves are now fixed: `StartBoardCallCommand` wraps room creation + identity provisioning + the DB insert in one transaction and calls `DeleteRoomAsync` (best-effort, logged, never masks the original exception) on any failure; the `EnsureUserIdentityAsync` half is covered by the same per-user distributed lock described below, so a failed `SaveChangesAsync` after identity provisioning can no longer race a concurrent caller into creating a second orphaned identity.
- `User.AcsCommunicationUserId` has no issuance/rotation/revocation metadata, so a row can silently point at an ACS identity deleted independently on Azure's side. Still open — no lifecycle owner for this exists yet; would need a dedicated reconciliation job, out of scope for this story.

## Deferred from: code review of 1-1-board-realtime-calls Task 3 (2026-07-25)

- **Resolved (2026-07-26).** Race condition in `EnsureUserIdentityAsync`'s check-then-act: two concurrent requests for the same user (e.g. starting a call on one board while joining another) could both see no `AcsCommunicationUserId` and both call `CreateUserAsync`, silently orphaning one identity via a last-writer-wins `UPDATE`. Fixed by having `StartBoardCallCommand` and `JoinBoardCallCommand` acquire a `user:{userId}:acs-identity` distributed lock (`IUnitOfWork.AcquireDistributedLockAsync`) inside the same transaction that commits `EnsureUserIdentityAsync`'s identity provisioning — a second concurrent caller now blocks until the first commits, then re-reads the user row fresh and sees the already-provisioned identity instead of racing to create a second one.
- **Resolved (2026-07-26).** `CreateRoomAsync` now passes `validFrom: <now>, validUntil: <now + 24h>` instead of `null, null`. No stated business rule caps call duration, so this is a safety-net upper bound only, not a real call-duration policy — normal calls are still torn down explicitly via `DeleteRoomAsync` when they end; this just bounds how long an abandoned room could outlive its `BoardCall` row if that explicit cleanup itself failed.
- No ACS emulator exists (unlike Azurite for Blob Storage) — local dev requires a real (or shared dev) Azure Communication Services resource just to boot the API once the connection-string check is strict, in addition to the dev-tunnel needed for Event Grid webhook testing (see Dev Notes §7). **Still open** — this is an infrastructure/tooling gap, not something fixable from application code.

## Deferred from: code review of 1-1-board-realtime-calls Task 4 & Task 5 (2026-07-25)

- **Resolved (2026-07-26).** Out-of-order Event Grid delivery isn't handled — a stale `CallParticipantAdded` arriving after a newer `CallParticipantRemoved` for the same participant would incorrectly reopen them as active. Fixed via a new `IBoardCallRepository.GetLatestParticipantAsync` (most recent row for a user+call, active or not): `RecordCallParticipantJoinedCommand` now skips the join if the latest known row is still active or was left at/after this event's `OccurredAt`; `RecordCallParticipantLeftCommand` now skips the leave if the currently-active row's `JoinedAt` is newer than this event's `OccurredAt` (a stale leave for a since-ended earlier session).
- **Consciously not changed (2026-07-26).** `BoardCallEventsController` relies on the same shared static `X-Internal-Api-Key` already used by every other `/api/internal/*` endpoint — a leaked key lets anyone forge participant join/leave events for any room/user. This is the pre-existing `InternalApiKeyMiddleware` architecture used across the whole codebase, not something specific to this story; changing it unilaterally here would touch every other internal endpoint's auth model. Revisit only as a cross-cutting security initiative if a per-integration secret or Azure AD auth for Event Grid delivery is ever warranted.
- **Resolved (2026-07-26).** `RecordCallParticipantJoinedCommand`/`RecordCallParticipantLeftCommand` (and, for consistency, `LeaveBoardCallCommand`): if `GetActiveCallWithParticipantsAsync` returns `null` because the call ended concurrently, the handler now skips sending the `CallParticipantsChanged` notification entirely instead of falling back to a stale/empty participant list.

## Deferred from: code review of 1-1-board-realtime-calls Task 6 & Task 7 (frontend) (2026-07-25)

- **Resolved (2026-07-26).** `StartCallAsync`/`JoinCallAsync`/`LeaveCallAsync`/`EndCallAsync` on `BoardCallStore` can race a concurrent real-time state change (a board switch, or another admin's `CallEnded` arriving while the response is in flight) and overwrite fresher `ActiveCall` state. Fixed with a generation counter (`_generation`): every one of those methods and every successfully-applied `ApplyAction` notification bumps it; `LoadActiveCallAsync` captures the generation before its GET and only applies the response if nothing fresher landed while it was in flight.
- **Resolved (2026-07-26).** `getParticipantId`'s fallback chain (`communicationUserId` → `.id` → `displayName` → `""`) in `acsCallInterop.js` could collide on `""`, and could theoretically collide with the `"local"` sentinel. Hardened with a `WeakMap`-backed per-participant-object fallback id (`unknown-participant-N`) used only when none of the real identifier fields resolve — guaranteed unique and never equal to `"local"`.
- **Consciously not changed (2026-07-26).** Node.js install in `src/Frontend/WebApp/Dockerfile` via `curl -fsSL https://deb.nodesource.com/setup_22.x | bash -` is unpinned (major version only) and unverified (no checksum). This is the exact snippet the story itself prescribed for Task 7 — changing it unilaterally would diverge from the story's own spec rather than fix a bug. Revisit only if the team explicitly wants to harden the install (pin a minor/patch version, verify a checksum).
- The bundle filename `acsCallInterop.bundle.js` is a magic string duplicated across `package.json`'s `outfile`, `AcsCallInteropService`'s module path constant, and `.gitignore`'s pattern, with nothing tying them together at compile time. Still open — maintainability nit, not worth a shared-constants mechanism at this scale.
- Remote participants' JS event listeners (`stateChanged`, `videoStreamsUpdated`, `isAvailableChanged`) are never explicitly unsubscribed via `.off(...)` when a participant leaves the call. Still open — likely garbage-collected with the departed participant object regardless; no observed leak.
- `IAcsCallInteropService.RemoteParticipantsChanged` has no documented subscribe/unsubscribe discipline beyond standard Blazor `OnInitialized`/`Dispose` hygiene, which `BoardCallPanel`/`BoardCallPreview` already follow. Considered resolved by convention; no further action.

## Deferred from: full story code review (2026-07-25)

- **Resolved (2026-07-26).** A board (or an entire workspace) can be soft-deleted while it has an active call — nothing called `IBoardCallLifecycleService.EndCallAsync` first, so the ACS room (and any still-connected participants) was never released. Fixed: `DeleteBoardCommand` now ends the board's active call (if any) before soft-deleting; `DeleteWorkspaceCommand` now ends every active call across the workspace's boards (via a new `IBoardCallRepository.GetActiveCallsForWorkspaceAsync`) before soft-deleting.
- **Resolved (2026-07-26).** The participant-capacity check retained a narrower residual race after the synchronous-reservation fix applied in the Task 4/5 round: two concurrent *new* joins could still both read the active-participant count before either's reservation row committed. Fixed: `JoinBoardCallCommand` now wraps the capacity check + seat reservation in a transaction guarded by a `boardcall:{callId}:participants` distributed lock, mirroring the same pattern already used by `CreateBoardCommand`/`CreateTaskCommand` for their own count-then-insert races.
- **Resolved (2026-07-26).** `StartBoardCallCommand`/`JoinBoardCallCommand`'s failure-recovery `catch` blocks called `SaveChangesAsync` again to persist the rollback — if that cleanup save itself threw, the original exception was masked and `DeleteRoomAsync`/rethrow never ran, leaking the ACS room. Fixed: cleanup steps are now wrapped in their own try/catch, logged on failure, and never allowed to suppress the original exception or skip the ACS room deletion attempt.
- **Resolved (2026-07-26).** `BoardCallStore.LoadActiveCallAsync`'s GET wasn't sequenced against concurrent push notifications. Fixed by the same generation-counter mechanism noted under the Task 6/7 section above.
