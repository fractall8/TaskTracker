# Deferred Work

## Deferred from: code review of 1-1-board-realtime-calls (2026-07-25)

- Global per-user single-active-call-across-boards constraint isn't enforced (a user could be "active" in calls on two different boards at once). Speculative, not covered by any stated AC.
- **Partially resolved by the Task 4 & Task 5 code review (2026-07-25).** No compensating cleanup for a partial ACS-Room-created/DB-insert-failed failure in the start flow — the Room-creation-then-DB-insert half is now fixed: `StartBoardCallCommand` wraps that section in a try/catch and calls `DeleteRoomAsync` on failure. **Still open**: the `EnsureUserIdentityAsync` half — if `SaveChangesAsync` fails for a reason unrelated to the room/participant insert (after `EnsureUserIdentityAsync` already created a new ACS identity via `CreateUserAsync` and mutated the tracked `User`), that ACS identity is orphaned on Azure's side with nothing local pointing to it. Applies to both `StartBoardCallCommand` and `JoinBoardCallCommand`. Needs either a compensating identity-delete on failure or acceptance as a narrow, rare gap.
- `User.AcsCommunicationUserId` has no issuance/rotation/revocation metadata, so a row can silently point at an ACS identity deleted independently on Azure's side. Revisit once Task 3's `IAcsCallService.EnsureUserIdentityAsync` exists to own this lifecycle.

## Deferred from: code review of 1-1-board-realtime-calls Task 3 (2026-07-25)

- **Partially resolved by the Task 4 & Task 5 code review (2026-07-25).** Race condition in `EnsureUserIdentityAsync`'s check-then-act: two concurrent requests for the same user can both see no `AcsCommunicationUserId` and both call `CreateUserAsync`, creating two ACS identities. The DB unique index (`IX_Users_AcsCommunicationUserId`) prevents silent duplicate persistence, and the loser's `SaveChangesAsync` now surfaces as a clean `ConflictException` (409) instead of an unhandled `DbUpdateException` (500), thanks to `UnitOfWork`'s new general unique-violation translation. **Still open**: no actual retry logic — the loser's Start/Join attempt just fails with a 409; the user has to manually click again rather than the system silently retrying/self-healing.
- `CreateRoomAsync` always passes `validFrom: null, validUntil: null`, deferring to ACS's default room TTL with no reconciliation against `BoardCall.EndedAt`'s lifecycle. Revisit once Task 4 establishes an actual call-duration business rule.
- No ACS emulator exists (unlike Azurite for Blob Storage) — local dev requires a real (or shared dev) Azure Communication Services resource just to boot the API once the connection-string check is strict, in addition to the dev-tunnel needed for Event Grid webhook testing (see Dev Notes §7).

## Deferred from: code review of 1-1-board-realtime-calls Task 4 & Task 5 (2026-07-25)

- Out-of-order Event Grid delivery isn't handled — a stale `CallParticipantAdded` arriving after a newer `CallParticipantRemoved` for the same participant would incorrectly reopen them as active. Needs per-participant sequencing state (e.g. compare `OccurredAt` against the row's last-updated timestamp) not currently modeled.
- `BoardCallEventsController` relies on the same shared static `X-Internal-Api-Key` already used by every other `/api/internal/*` endpoint — a leaked key lets anyone forge participant join/leave events for any room/user. Pre-existing `InternalApiKeyMiddleware` architecture, predates this story; revisit if a per-integration secret or Azure AD auth for Event Grid delivery is ever warranted.
- `RecordCallParticipantJoinedCommand`/`RecordCallParticipantLeftCommand`: if `GetActiveCallWithParticipantsAsync` returns `null` because the call ended concurrently with the webhook's processing, the fallback `?? call` sends a `CallParticipantsChanged` notification with an empty participant list instead of skipping it. Self-corrects on the next fetch; low priority.

## Deferred from: code review of 1-1-board-realtime-calls Task 6 & Task 7 (frontend) (2026-07-25)

- `StartCallAsync`/`JoinCallAsync` on `BoardCallStore` can race a concurrent real-time state change (a board switch, or another admin's `CallEnded` arriving while the response is in flight) and overwrite fresher `ActiveCall` state. The board-switch half should be guarded alongside the `LoadActiveCallAsync` staleness fix (capture the requested `BoardId`, only apply if it still matches on completion); the narrower "call ended by someone else during my own in-flight Join" case would need a generation counter or similar to fully close — low-probability, largely self-correcting.
- `getParticipantId`'s fallback chain (`communicationUserId` → `.id` → `displayName` → `""`) in `acsCallInterop.js` could collide on `""` for a participant with none of those fields, and the `"local"` sentinel could theoretically collide with a real participant id equal to that literal string. Not realistically reachable — this app always provisions ACS Communication User identities (always populates `communicationUserId`), and ACS ids are never literally "local".
- Node.js install in `src/Frontend/WebApp/Dockerfile` via `curl -fsSL https://deb.nodesource.com/setup_22.x | bash -` is unpinned (major version only) and unverified (no checksum) — a real supply-chain/reproducibility hardening opportunity, but it's the exact snippet the story itself prescribed for Task 7; revisit only if the team wants to diverge from that.
- The bundle filename `acsCallInterop.bundle.js` is a magic string duplicated across `package.json`'s `outfile`, `AcsCallInteropService`'s module path constant, and `.gitignore`'s pattern, with nothing tying them together at compile time. Maintainability nit, not worth a shared-constants mechanism at this scale.
- Remote participants' JS event listeners (`stateChanged`, `videoStreamsUpdated`, `isAvailableChanged`) are never explicitly unsubscribed via `.off(...)` when a participant leaves the call — likely garbage-collected with the departed participant object regardless.
- `IAcsCallInteropService.RemoteParticipantsChanged` has no documented subscribe/unsubscribe discipline — standard Blazor `OnInitialized`/`Dispose` hygiene, a Task 8 concern when its UI components subscribe to this event.
